# Backend Internals Reference

Technical reference for all inference backends used in `model_benchmark_ros.py` / `model_adapter.py`.
Covers model artifacts, adapter classes, vAccel session types, C-layer interfaces, and exactly what each timing metric captures.

## What `inference_ms` captures per backend

`inference_ms` is measured with `time.perf_counter_ns()` bracketing `adapter.infer()`, followed by `torch.cuda.synchronize()` if `TORCH_DEVICE` is CUDA.

### `ptc`

```
[ inference_ms ]
  input_tensor.to(device)       ← CPU→GPU H2D (if GPU)
  model_final(input_tensor)     ← Inductor/Triton compiled forward
  output.detach().cpu()         ← GPU→CPU D2H + implicit sync (if GPU)
[ + outer torch.cuda.synchronize() ]
```

Includes host-to-device and device-to-host transfers. CUDA sync is redundant (`.cpu()` already forces it) but harmless.

### `aoti`

```
[ inference_ms ]
  input_tensor.to(device)       ← CPU→GPU H2D (if GPU)
  model_final(input_tensor)     ← AOTInductor pre-compiled native callable
  output.detach().cpu()         ← GPU→CPU D2H + implicit sync (if GPU)
[ + outer torch.cuda.synchronize() ]
```

Same shape as `ptc`. Model is loaded once via `torch._inductor.aoti_load_package()` and called as a pre-compiled native callable — no JIT compilation at first call.

### `sol`

```
[ inference_ms ]
  np.copyto(input_buffer, input_numpy)    ← copy into pre-allocated shared buffer
  model.run(*execution_args)              ← SOL .so DNN engine (CPU or GPU)
  [ model.sync() if available ]           ← force completion for GPU
[ no outer CUDA sync — TORCH_DEVICE is cpu for SOL ]
```

No allocation in the hot path. `output_buffer` is the same pre-allocated ndarray returned directly.

### `vaccel-local-ptc`

```
[ inference_ms ]
  vaccel_torch.Tensor.from_torch(input)   ← wrap CPU torch.Tensor as vAccel tensor
  session.torch_model_run(model, [t])     ← vAccel C API dispatch → local torch plugin
    └─ libvaccel-torch.so                 ← C shared library
         └─ AOTInductor forward()         ← pre-compiled Triton kernels
              ├─ H2D (if GPU)
              ├─ kernel execution
              └─ D2H (if GPU)
  outputs[0].as_torch().detach().clone()  ← unwrap vAccel tensor → CPU torch.Tensor
[ + outer torch.cuda.synchronize() if GPU ]
```

Includes the vAccel Python→C dispatch overhead (`from_torch` / `as_torch`) on top of actual inference. For GPU runs, H2D/D2H happen inside `torch_model_run`.

### `vaccel-local-sol`

```
[ inference_ms ]
  np.copyto(input_buffer, input_numpy)    ← copy into pre-allocated shared buffer
  model.run(*execution_args)              ← SOL/vAccel Python wrapper
    └─ libvaccel.so                       ← vAccel C library (local dispatch)
         └─ libvaccel-exec.so             ← exec plugin
              └─ libsol_{model}_wrapper.so← SOL vAccel wrapper .so
                   └─ libsol_{model}.so   ← SOL DNN engine (CPU or GPU)
[ no outer CUDA sync ]
```

Same calling convention as pure `sol` from the adapter side. The overhead vs. `sol` is one extra vAccel C dispatch layer (through `libvaccel-exec.so`) inside the wrapper.

### `vaccel-remote-ptc`

```
[ inference_ms ]   ← measured on the robot (client side)
  vaccel_torch.Tensor.from_torch(input)   ← serialize CPU torch.Tensor
  session.torch_model_run(model, [t])     ← vAccel C API → RPC plugin
    └─ libvaccel-rpc.so                   ← C library, ZeroMQ transport
         │── TCP send ──────────────────► vaccel-rpc-agent (REMOTE_HOST:9125)
         │                                  └─ libvaccel-torch.so
         │                                       └─ AOTInductor forward()
         │                                            ├─ H2D (TARGET_DEVICE)
         │                                            ├─ kernel execution
         │                                            └─ D2H
         └── TCP receive ◄──────────────── serialized output tensor
  outputs[0].as_torch().detach().clone()  ← deserialize → CPU torch.Tensor
[ no outer CUDA sync — TORCH_DEVICE=cpu on robot ]
```

`inference_ms` = **full RPC round-trip**: client serialization + TCP send latency + remote execution on `TARGET_DEVICE` + TCP receive latency + client deserialization.

Robot always uses `TORCH_DEVICE=cpu` (preprocessing only); `CUDA_VISIBLE_DEVICES=""` and `VACCEL_TORCH_CUDA_ENABLED=0` are set when `device=cpu` to prevent CUDA initialization.

### `vaccel-remote-sol`

```
[ inference_ms ]   ← measured on the robot (client side)
  np.copyto(input_buffer, input_numpy)    ← copy into pre-allocated shared buffer
  model.run(*execution_args)              ← SOL/vAccel Python wrapper
    └─ libvaccel.so → libvaccel-rpc.so   ← ZeroMQ/TCP transport (inside SOL wrapper)
         │── TCP send ──────────────────► vaccel-rpc-agent (REMOTE_HOST:9125)
         │                                  └─ libvaccel-exec.so (exec plugin)
         │                                       └─ libsol_{model}_wrapper.so
         │                                            └─ libsol_{model}.so (TARGET_DEVICE)
         └── TCP receive ◄──────────────── serialized output buffer
  output_buffer populated
[ no outer CUDA sync ]
```

Same as `vaccel-remote-ptc` in terms of transport; differs only in the execution engine on the remote side (SOL via exec plugin vs AOTInductor via torch plugin).

## C-layer interfaces

### `ptc` — no explicit C interface in user code

`torch.compile` calls Inductor, which generates Triton kernels and compiles them to native code via the PyTorch C++ dispatcher internally. No user-visible C API or `ctypes`/`cffi` call.

### `sol` — Python → SOL `.so` via Python wrapper (ctypes/cffi inside)

The SOL-generated `sol_{model}.py` wrapper loads and calls the compiled `.so` internally (ctypes or cffi, depending on the SOL wrapper generator). From the adapter, the interface is plain Python: `model.run(*numpy_arrays)`. No `vaccel` import is needed.

### `vaccel-local-ptc` and `vaccel-remote-ptc` — vAccel Python bindings → `libvaccel.so`

The adapter calls the vAccel Python package (`import vaccel`, `import vaccel.ops.torch as vaccel_torch`), which are thin Python bindings over the vAccel C library:

- `vaccel.Session(plugin_type)` → `vaccel_session_init()` in `libvaccel.so`
- `vaccel.Resource(path, type)` → `vaccel_resource_new()` in `libvaccel.so`
- `session.torch_model_load(model)` → `vaccel_torch_jmodel_load()` C function
- `session.torch_model_run(model, tensors)` → `vaccel_torch_jmodel_run()` C function
- `vaccel_torch.Tensor.from_torch(t)` / `.as_torch()` → tensor serialization helpers in the bindings

For local: `libvaccel.so` dispatches to `libvaccel-torch.so` (torch plugin).
For remote: `libvaccel.so` dispatches to `libvaccel-rpc.so` (RPC plugin) which opens a ZeroMQ socket to the agent.

### `vaccel-local-sol` and `vaccel-remote-sol` — SOL wrapper → vAccel C API → exec plugin (hidden)

`gen_sol_vaccel_wrappers.py` generates the `lib_{device}/vaccel/` directory by:
1. Copying vAccel-specific wrapper templates from `scripts/sol_vaccel_wrappers/templates/{model}/`
2. Running `make` to compile `libsol_{model}_wrapper.so`, which links against the original `libsol_{model}.so` (and its vendor DNN backends) from the parent `lib_{device}/`
3. Generating a dlopen manifest

`VaccelSolAdapter` loads from this `vaccel/` directory and passes `use_remote=True/False` to the generated wrapper constructor. The wrapper creates its own `vaccel.Session` and dispatches through vAccel internally: `libvaccel.so` → `libvaccel-exec.so` (exec plugin) → `libsol_{model}_wrapper.so` → `libsol_{model}.so`. For remote variants, `libvaccel-rpc.so` replaces the local dispatch and carries the call over ZeroMQ/TCP to the agent, where the exec plugin runs the wrapper `.so` on the target device. From the adapter's perspective the interface is identical to pure `sol`: `model.run(*numpy_arrays)`.

## Summary: local vs remote

The sole code difference between `vaccel-local-*` and `vaccel-remote-*` is the plugin type in the vAccel session:

```python
# local
vaccel.Session(PluginType.TORCH)             # ptc adapter  → libvaccel-torch.so
model_class(path=lib_path, use_remote=False) # sol wrapper  → libvaccel-exec.so → libsol_{model}_wrapper.so

# remote
vaccel.Session(PluginType.TORCH | PluginType.REMOTE)   # ptc adapter  → libvaccel-rpc.so → remote libvaccel-torch.so
model_class(path=lib_path, use_remote=True)             # sol wrapper  → libvaccel-rpc.so → remote libvaccel-exec.so → libsol_{model}_wrapper.so
```

`PluginType.REMOTE` makes `libvaccel.so` select the RPC plugin (`libvaccel-rpc.so`) instead of the local plugin. All model file formats, preprocess types, and postprocess steps are identical. The only runtime differences are:

- Model binary is sent to the agent over TCP at `load_model()` time (once per session).
- Each `infer()` call pays the full TCP round-trip cost instead of an in-process function call.
- The agent process has no ROS/DDS threads: inference runs in the `vaccel-rpc-agent` container, which has no `rclpy.spin` thread and no DDS middleware threads. For local variants, those threads share CPU cores with OpenMP workers; if a DDS thread preempts one OMP worker mid-parallel-region, every other worker stalls at the end-of-region barrier waiting for it, inflating and destabilizing latency (observed: 23–242 ms with OMP=12 for `vaccel-local-ptc`; stable ~82 ms with OMP=1). The remote agent runs its OMP workers uncontested at full thread count.
